# Known issues

## 1. Compile errors because of no type deduction

The language doesn't feature type deduction.
This is completely fine in most cases, but issues arise whenever `TypeToken::None` is on the `TargetTypeStack`.
Consider the following piece of code:

```
i32 x = 10
if (1 < x)
  ...
end
```

The condition of the `IfExpression` is a `BinaryExpression` with an `IntergerValueExpression` on the left-hand side and a `VariableExpression` on the right-hand side.
As mentioned in [determining target types during code generation](./technical_documentation.md#4-2-2-determining-target-types-during-code-generation), `IntegerValueExpressions` need to determine their target type during code generation via the `TargetTypeStack`.
However, the only expression that can push a type onto the `TargetTypeStack` before the `IntegerValueExpression` is codegened is the `IfExpression`, because the `BinaryExpression` doesn't know what type to generate (because of the missing type deduction), so it assumes that the previous expression pushed the correct target type onto the `TargetTypeStack`.
It then pushes the type generated by its left-hand side expression onto the `TargetTypeStack` before codegening its right-hand side expression.
This is the reason why `IfExpressions` push `TypeToken::None` onto the `TargetTypeStack`: to allow the `IntegerValueExpression` to generate its default type.
Otherwise, the `IntegerValueExpression` would try to generate whatever type the `IfExpression` expects its condition to generate (most likely `TypeToken::Bool`).

This would lead to:

- ... (in my opinion) unexpected error messages (in this example `[ Compile error ]: type mismatch: can't create a value of type 'bool' from an integer value`),
- ... having to cast `literal expressions` in the condition of an `IfExpression` (`if (i32(1) + x)`),

both of which I wanted to avoid.
However, this decision still results in the following compile errors.

### 1.1 Possible type mismatch errors when using yoda conditions

In case you are unfamiliar with yoda conditions, check out the [wikipedia article](https://en.wikipedia.org/wiki/Yoda_conditions).

Yoda conditions will cause a `[ Compile error ]: type mismatch: ...` if the types of the literal and variable being used are different:

```
i32 a = 0
f32 b = 0.0

bool w = a > 0    # works fine, a evaluates first and sets the target type for 0 to TypeToken::Int32
bool x = 0 < a    # works fine, 0 evaluates to its default type (i32), which matches the type of a
bool y = b > 0    # works fine, b evaluates first and sets the target type for 0 to TypeToken::Float32
bool z = 0 < b    # compile error, 0 evaluates to its default type (i32), which doesn't match the type of b
```

## 2. Possible compile error when codegening a function

At the beginning of `Kepler::AST::Function::codegen()`, the function checks whether a function with the same name already exists in LLVM's IR.
However, the function only checks for an existing LLVM IR and does not validate the actual signature of the AST node against the signature of the existing LLVM IR.
This means that a previous ‘extern’ declaration takes precedence over signature of the current function, which can cause `codegen` to fail (e.g. if the function arguments are named differently).
